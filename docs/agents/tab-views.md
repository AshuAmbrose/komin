# 10.1 Tab views

Section 10.1 of the agent docs. [AGENTS.md](../../AGENTS.md) is the core (rules, commands, pitfalls, open work), loaded into every session, and lists every file in this folder; read its sections 0–2 first. "Section N" and "pitfall N" below mean AGENTS.md's numbering, and section 10.x is a file here.

- **Lifecycle** (UI → main):
  - `webviews.add(tabId)` sends `createView` with the list of page events to forward.
  - `webviews.setSelected` sends `setView`.
  - `webviews.update(tabId, url)` runs `urlParser.parse`, then sends `loadURLInView`.
  - `webviews.destroy` sends `destroyView`.
- **Page events** reach the UI as `view-event` and are dispatched to `webviews.bindEvent(name, fn)` handlers. Main drops subframe `did-start-navigation`/`will-redirect` and subframe `did-navigate-in-page` events.
- **`callViewMethod`** calls a method or sets a property on the view's `webContents`, then replies `async-call-result`. History methods (`canGoBack`, `goBack`, `goToIndex`, ...) are called on `webContents.navigationHistory`, since the `webContents` versions are deprecated. Callers use `webviews.callAsync(id, method, argsOrCallback, callback)`.
- **Popups** reuse the default web preferences. `filterPopups(url)` in `filtering.js` blocks popups that the ad-block engine matches.
- **Every window a page opens is Chromium's, shown as a tab** (since 2026-11-17). The window-open handler in `viewManager.js` allows `window.open()` and links that open a new tab, and the UI shows the new `webContents` as a tab (`did-create-popup` in `js/browserUI.js`): in the background for Ctrl+click and middle-click (`disposition: 'background-tab'`, unless the setting `openTabsInForeground`), in front otherwise. The page gets its window, the new page its `window.opener`, and names work, as in Chrome. A private tab's window is made by Chromium in its opener's session, so its tab records that session (`partition`, `js/tabState/tab.js`) and `webviews.add` uses it when the tab is created again after hibernation; before, such a tab woke up in a new empty session. Suite `popups` (15 checks; `MIN_TEST_OLD=popupsAsNewTabs` puts the old rule back, and then 6 window and private-tab checks fail while the link checks pass both ways) and `popups-real` (real sites' sign-in buttons). Web-platform-tests after the change (`wpt.js run min @compare`, then `compare`, 2026-11-17): 7 of 1,854 pages fail only in Min, from 107; left are a pop-up closing itself (`window.close()`) while it has a `beforeunload` handler (2), a nested `_parent` lookup (1), muted autoplay (3, section 10.6) and a notification test that needs WebDriver to grant the permission (1).
- **Opened tabs outlive their opener** (since 2026-11-24, pitfall 66). The window-open handler answers `outlivesOpener: true`: by default Electron closes a page's windows when the page closes, which, once every link-opened tab was such a window (2026-11-17), emptied every tab a page had opened when it closed. Suite `popups` checks a `window.open` tab, a `target="_blank"` link and a Ctrl+click survive their opener. Code walking `viewMap` (`notifyExtensionPages`, the Web Store's, `extensionsTabCreated`, the extension tab list) and `destroyView` check that a view still has its `webContents`.
- **Min's own pages have security rules** (Content-Security-Policy, since 2026-11-24, from upstream's 29cb4d31): every `min://` response gets `script-src 'self'; style-src 'self'; object-src 'none'; form-action 'self'` from `main/minInternalProtocol.js` (`getInternalPageCSP`; the translation service and its Bergamot worker files also get `'wasm-unsafe-eval'`), and most pages a stricter `<meta>` of their own (`default-src 'self'`, no `<base>`, no forms; the interface and reader view `img-src * data: blob:`, Settings `img-src 'self' data:`, the PDF viewer and the interface `connect-src *`). No inline scripts or style attributes: the session restore error page's script moved to `sessionRestoreError.js`, Settings' inline styles to `settings.css`. Suite `internal-pages` opens each page (and the interface with an extension's toolbar icon) and fails on any "Refused to ..." Chromium prints for a `min://` page. Not opened there: the sign-in prompt (covered by `security-checks` B5).
- **Until 2026-11-17, `window.open(url)` without features got no window back** (upstream's rule; measured 2026-11-14 with web-platform-tests, `test/e2e/wpt.js`). The handler took an open without `features` for a link click (upstream issue #1835): it asked the UI for a new tab (`new-tab`) and denied Chromium's window. So the page's `window.open(url)` returned `null`, and the new tab had no `window.opener` and no name the page could target again. With features (`window.open(url, 'x', 'width=500')`), or for `about:blank`, Chromium's window was allowed and became a tab, linked to its opener. Measured: of 1,854 test pages, 107 pass in a bare Electron app with the same Chromium and fail in Min (334 subtests); 102 of them open windows (99 found by `wpt.js compare`'s `opensWindows`, three more from helper files it can't read), mostly waiting for a message from the new window or reading `w.closed`. With this rule switched off for one run (then `MIN_WPT_SWITCH=popupsKeepOpener`, which sent every open through the popup path; since the change the switch is `popupsAsNewTabs`, which puts the rule back), 99 of the 107 pass, and of the 245 window subtests that failed only in Min, 24 still do: closing a pop-up tab from its own script (`window.close()`, with `beforeunload`), `history.length` in pop-ups, one nested `_parent` lookup. The other 5 of the 8 broken tests aren't about windows (autoplay, section 10.6; notifications, section 10.3). On real sites that's a sign-in or payment page opened with `window.open(url)` and no features, which reports back through `window.opener.postMessage` or is watched through `w.closed`: the page throws (`w` is `null`) or never hears back. Not seen on a real site (many sign-in pop-ups pass a size, which avoided it). Changed 2026-11-17 at the maintainer's request (above).
- **Internal pages are Min's to open** (since 2026-11-13, pitfall 57). A navigation, redirect or `window.open` to a `min:` address is refused (`will-frame-navigate`, `will-redirect`, the window-open handler in `viewManager.js`) unless Min started it (`loadURL`: the address bar, session restore, the error page after a failed load, the PDF viewer, the userscript install page) or an internal page did (its `initiator`). Before, a website could send its own tab, or a popup it had opened, to any internal page with parameters it chose. Extensions still can (`tabs.create`), as Chrome lets them open `chrome://` pages, so each internal page checks its own parameters.
- **The address shown while a page loads** (since 2026-11-13, pitfall 59). Main adds a last argument to `did-start-navigation` and `will-redirect`: whether the page itself started the navigation (`initiator` set). The UI (`onNavigate` in `js/webviews.js`) only shows Min's own navigations' addresses at the start; a link or a script's navigation shows its address once its page arrives (`did-navigate`), as in Chrome. And when a tab stops loading, its address is checked against the page that's there (`showLoadedAddress`, on `did-stop-loading`): a typed address that ended without a page (204 No Content, a download) goes back to the page. Before, a page could put another site's address over its own content by starting a navigation that never arrived. Code that needs the tab a response is for gets the tab's id from main (`openPDF`, `set-file-view`), not the address. Measured (`security-checks` B2): a page's own navigation to a 204 address and a typed one both leave the address bar on the page that's there.
