Chapter 01

What a browser is made of

A browser has two halves. Min only writes one of them.

Every browser is split into an engine and a shell. The engine reads HTML, CSS and JavaScript and turns them into pixels on screen. The shell is everything around the page that you click: tabs, the address bar, history, settings, the download bar, ad blocking.

Chrome, Edge, Brave, Opera and Vivaldi all use the same engine, Chromium, and differ mostly in their shells. Chromium itself is made of parts you will hear about:

  • Blink lays out and draws HTML and CSS.
  • V8 runs JavaScript.
  • The network stack downloads everything a page asks for.
  • The GPU process sends the finished drawing to your graphics card.

Electron packages Chromium together with Node.js so people can build desktop apps in JavaScript. VS Code, Discord and Slack are Electron apps. Node.js is what lets JavaScript read files, start programs and do other things a web page is never allowed to do.

Min is a shell written on top of Electron. That has a surprising consequence: Min's own interface is a web page. The tab bar and address bar are HTML in index.html, styled with CSS and driven by JavaScript. Websites you visit are shown on top of that page.

So working on this browser almost never means touching the engine, which is millions of lines of C++. It means writing JavaScript that tells Chromium what to do through Electron's APIs.

In your fork

Upstream Min is written by PalmerAL and others; your repository AshuAmbrose/komin follows it and adds your own work. Your additions are a permission manager, a low-resource mode (memory trimming, memory priority and tab hibernation), the Ghostery ad blocker and Tampermonkey-style userscripts. Chapter 02

Processes

This is the most important idea in the guide. Everything else follows from it.

A process is a running program with its own memory. Programs can't read each other's memory. Chromium uses that on purpose: it runs each part of the browser in a separate process, so a crashing tab doesn't take down the browser, and a malicious site can't read your other tabs or your files.

Open Task Manager while Min runs and you'll see several Min.exe entries. When I measured a session with one tab open, it looked like this:

The main process

There is exactly one. It starts first, creates windows, owns every tab's web view, hooks into every network request, reads and writes files, and shows menus. It has full Node.js. If it crashes, the whole browser closes. In Min its code lives in main/ and runs as one file, main.build.js.

Renderer processes

A renderer is a process that shows a web page. Min has two kinds, and the difference between them matters for security:

  • The browser UI Browser UI is Min's own page, index.html. Because it's Min's own code, it is trusted and gets Node.js: nodeIntegration: true, contextIsolation: false (see createWindowWithBounds in main/main.js).
  • Website tabs Web page run code from the internet, so they're locked down: sandbox: true, contextIsolation: true, nodeIntegration: false (see getDefaultViewWebPreferences in main/viewManager.js). Chromium also gives each site its own process (site isolation). That's why an ad-heavy news site with many ad frames can spawn dozens of processes.
The one rule never to break

Never load a website into a renderer that has Node.js. A web page with Node.js can read your files, run programs and steal saved passwords. Min keeps websites in sandboxed views and its own UI in a separate, trusted view.

Preload scripts: the bridge

A sandboxed page can't do anything privileged, but the browser still needs to know things about it: its text (for history search), whether it has a login form, whether it's using the camera. A preload script is the answer. It's a script that Electron runs inside the page's renderer before the page's own scripts, with a small extra power: it can send messages to the main process.

The preload runs in its own isolated world. It sees the same page (the same DOM), but it has its own separate set of JavaScript variables, so the page can't see or change it. The page's own code runs in the main world. When a preload needs to change how the page's JavaScript behaves, it has to inject code into the main world, and that code is visible to the page. Chapter 08 covers this in detail.

Chapter 03

How processes talk

Processes can't share variables, so they send each other messages. This is called IPC: inter-process communication.

An IPC message has a channel name (a string like 'createView') and some data. The data is copied, not shared, so it can only contain plain values: strings, numbers, arrays, plain objects. Functions, DOM elements and class instances can't be sent.

callAsync: a remote control for tabs

The UI often needs to ask a tab a question ("can you go back?") or tell it to do something ("reload"). Tabs are objects in the main process, so the UI can't call them directly. webviews.callAsync(tabId, method, args, callback) sends callViewMethod to the main process, which calls that method on the tab's webContents and sends the result back as async-call-result.

// js/navbar/navigationButtons.js: is the back button enabled?
webviews.callAsync(tabs.getSelected(), 'canGoBack', function (err, canGoBack) {
  if (!err) backButton.disabled = !canGoBack
})
Tip

Every message has a sender and a receiver that share a channel name. To find the other end of any message, search the whole project for its name, for example set-window-title.

The surprise in main/

In most Node.js projects, each file is a module with require and module.exports. Min's main-process files are different: scripts/buildMain.js glues them together, in a fixed order, into one big file, main.build.js. Everything declared at the top of one file is visible in all the others. That's why viewManager.js can call sendIPCToWindow (defined in main.js) and windows (defined in windowManagement.js) without importing them.

  • Order matters for code that runs immediately at load time, but not for code inside functions that runs later.
  • The lint check (npm test) doesn't know about the gluing, so it reports hundreds of "X is not defined" errors that aren't real.
  • Your fork's code often writes typeof isTabActiveWithMedia === 'function' before calling a function from another file. That guard does nothing in the real bundle, but it's harmless.

The browser UI code in js/ is different again: it does use require, and the tool browserify bundles it. Its paths are relative to js/, so you'll see require('tabState.js') without a js/ prefix.

Chapter 05

Startup, step by step

What happens between double-clicking Min and seeing your tabs.

  1. Electron starts the main process. It reads "main": "main.build.js" from package.json and runs that file. In development you start this with npm start, which builds everything and runs electron . --development-mode.

  2. Top-level code in main/main.js runs. In order:

    • the crash reporter starts (local only, nothing is uploaded);
    • Windows installer events are handled: on install, registryConfig.js registers Min as a browser with Windows;
    • the profile folder is chosen, with -development added in development mode;
    • settings.json is read;
    • Chromium options are set, such as --js-flags=--optimize-for-size (only if it's turned on in Settings → Performance, Chapter 12, which is why this comes after reading the settings);
    • the language is chosen;
    • requestSingleInstanceLock runs: if Min is already open, this second copy hands over its links and quits.

  3. Electron fires app.on('ready'). Min registers the min:// protocol (registerBundleProtocol) and calls createWindow().

  4. The window is built (createWindowWithBounds). It reads the last size and position from windowBounds.json, creates a frameless BaseWindow, and puts one WebContentsView inside it for the UI. That view loads min://app/index.html and gets startup arguments such as --user-data-path and --window-id.

  5. The UI page starts. index.html loads dist/bundle.js, which runs js/default.js. It reads the arguments into window.globalArgs, creates globals like ipc, then requires each feature module and calls its initialize().

  6. Your tabs come back. The last line of default.js calls sessionRestore.restore(), which reads sessionRestore.json and rebuilds your tasks and tabs. Only the selected tab loads straight away.

  7. Background helpers start. The main process opens a hidden window for history search (placesService.html), and the ad-blocking engine loads from its cache file.

Two helpers you'll see everywhere

  • getWindowWebContents(win) returns the UI page of a window (the first child view).
  • sendIPCToWindow(win, channel, data) sends a message to that window's UI. If the UI is still loading it waits for it, and it skips windows that have been closed.
Chapter 06

The browser UI

Tabs, tasks, the address bar and the suggestion list. All of this code runs in the UI renderer.

The trick with screenshots

Each website is a native view drawn on top of the UI page, and HTML can never be drawn above a native view. So when Min needs HTML to cover the page (the address-bar dropdown, the task overview), it takes a screenshot of the page, hides the real view, and shows the screenshot in its place. That's what webviews.requestPlaceholder(reason) and webviews.hidePlaceholder(reason) do. If you ever notice that the page looks frozen while the address bar is open, this is why.

The data model: tasks contain tabs

Min groups tabs into tasks (other browsers call them tab groups or workspaces). The code in js/tabState/ keeps this in two global objects:

  • tasks is a TaskList, every task you have.
  • tabs is the TabList of the task that's currently selected.

A tab is a plain object with fields such as id, url, title, private, loaded, muted, hasAudio, scrollPosition and previewImage. A task has id, name, tabs and tabHistory (for reopening closed tabs).

// read and change tabs (try this in the UI's DevTools console, Chapter 15)
tabs.get()                                // copies of all tabs in this task
tabs.get(tabs.getSelected()).url          // the selected tab's address
tabs.update(tabs.getSelected(), { muted: true }) // changes the icon only; see Exercise 1
tasks.on('tab-updated', function (id, key) { console.log(id, key) })
  • get() returns copies, so editing the object you got back changes nothing. Always change tabs with update().
  • Every change fires an event (tab-added, tab-updated, tab-selected, tab-destroyed and the task versions of these). Listeners run together a moment later, not immediately.
  • js/sessionRestore.js saves this model to sessionRestore.json every 30 seconds, leaving private tabs out.
  • With several windows open, js/windowSync.js forwards every event through the main process so all windows agree.

Chapter 07

Following one page load

You type an address and press Enter. Here is every step, with the file that handles it.

  1. UI js/navbar/tabEditor.js sees Enter and calls searchbar.openURL. If you typed a !bang, its handler takes over. Otherwise the searchbar emits url-selected.

  2. UI js/browserUI.js hears url-selected and calls webviews.update(tabId, url). urlParser.parse turns example.com into https://example.com, or turns plain words into a search address.

  3. Main The message loadURLInView reaches main/viewManager.js, which calls webContents.loadURL(url) on that tab's view.

  4. Network Chromium requests the page, and then its scripts, images and so on. For every request, Min's hooks run in the main process: filtering.js removes tracking parameters and blocks ads, UASwitcher.js adjusts the browser identity it reports, and download.js checks the response (is it a PDF? a download?).

  5. Page A renderer starts for the site, and dist/preload.js runs before the site's own scripts. Among other things it asks the main process for the ad blocker's hiding rules for this site.

  6. UI Page events flow back as the page loads: did-start-loading, did-navigate, page-title-updated. webviews.js passes each one to its listeners, which call tabs.update(id, {url, title}). That fires tab-updated, so the tab bar redraws the title and setWindowTitle updates the window title.

  7. Page After loading, the preload sends the page's text (pageData) so it can be searched in history later. It also sends whether reader view would work (canReader). The UI captures a screenshot for the tab preview.

The two worlds

The preload runs in an isolated world: same DOM, separate JavaScript variables. A site can't change the preload's functions. Sometimes, though, Min has to change how the site's JavaScript behaves. Examples are replacing window.WebSocket to count connections, wrapping getUserMedia to notice camera use, and the ad blocker's scriptlets. That code must be injected into the site's main world with webFrame.executeJavaScript.

Know the limits of main-world code

Anything injected into the main world can be seen and undone by the site. That's fine for site fixes and ad blocking, but don't rely on it for security. For example, the camera indicator from mediaTracker.js is best-effort: a hostile page could read its secret token and send fake "stopped" messages.

Chapter 09

The network layer

Every request any tab makes passes through hooks in the main process.

Electron gives each session (a set of cookies, cache and storage; normal tabs share one, each private tab gets its own) a webRequest object with hooks for each stage of a request. Min uses four:

HookFileWhat Min does there
onBeforeRequestmain/filtering.jsRemoves tracking parameters like utm_source and fbclid from addresses; blocks ads and trackers; optionally blocks all scripts or images.
onBeforeSendHeadersmain/UASwitcher.jsSends a Firefox identity to Google's sign-in page, because Google refuses sign-in from unfamiliar Chromium browsers. Sets the Client Hints headers for other sites.
onHeadersReceivedmain/download.jsSends PDFs to Min's viewer; marks files versus pages; lets reader and PDF pages read the documents they show; adds the ad blocker's CSP rules.
onBeforeRedirectmain/download.jsRemembers redirects so downloads get the right name.
Why CSP code sits in download.js

Electron allows only one listener per hook per session. Since download.js already owns onHeadersReceived, the ad blocker's header changes are applied from there, through applyFilteringCSPHeaders.

These hooks also decide whether extensions can filter requests. As long as any of them is there, Electron switches off request filtering for every extension in that session, so uBlock Origin Lite would block nothing. When you let such an extension take over, Min removes all four from normal tabs and does their other jobs another way (Chapter 18).

Ad blocking

The part of the browser you've worked on most. It reuses uBlock Origin's rules and Ghostery's engine instead of writing a blocker from scratch.

Filter lists: the rules

Ad blockers don't know what an ad is. They follow filter lists: big text files of rules maintained by volunteers (EasyList, uBlock Origin's lists). There are three kinds of rule, and each needs a different mechanism:

! 1. network rule: don't download anything from this domain
||doubleclick.net^
! 2. cosmetic rule: hide matching elements on youtube.com
youtube.com##ytd-ad-slot-renderer
! 3. scriptlet rule: run a small script on youtube.com that
!    removes ad data before YouTube's player reads it
youtube.com##+js(set-constant, ytInitialPlayerResponse.playerAds, undefined)

The engine's life cycle in main/filtering.js

Network blocking

handleRequest runs for every request:

  • It works out which site is asking (details.initiator).
  • It skips sites you've excepted with the shield button.
  • It strips tracking parameters.
  • It asks the engine with adblockerEngine.match(request). The answer is either "cancel" (the request fails with ERR_BLOCKED_BY_CLIENT) or "redirect" to a harmless empty file.

Min's original filter parser still runs as well, for Min's own few rules and any you put in customFilters.txt in the profile folder.

Hiding elements and running scriptlets

When a page starts, js/preload/default.js sends one request, page-start, and waits for the answer (the same answer brings the page's userscripts, so the page waits once, not twice). The main process (injectCosmeticFiltersForSender) asks the engine for the rules for that site:

  • CSS rules are inserted by the main process with insertCSS(..., {cssOrigin: 'user'}), so they beat the site's own styles.
  • Scriptlets go back to the preload, which runs them in the page's main world straight away, before the page's own scripts (see "Why YouTube showed ads" below).

The YouTube bug, and why the wrapper exists

YouTube gets about 34 scriptlets. Each one arrives bundled with its own copy of uBlock Origin's helper functions (such as proxyApplyFn and safeSelf). uBlock Origin itself runs all scriptlets together, sharing one copy of the helpers. Ghostery's built-in injector (onInjectCosmeticFilters) instead runs each one as a separate top-level script. Here's what went wrong:

  1. Each new copy of proxyApplyFn replaced the global one.
  2. The first copy's wrapper around Function.prototype.toString then read the last copy's settings, which pointed back at itself.
  3. Calling toString on any function now recursed forever.
  4. YouTube's page code converts functions to text while building its components, so the components crashed. You saw search results without views or dates, and Shorts that never built a player.

// each scriptlet runs in its own function, so its helper copies can't overwrite the others,
// but all of them get the same scriptletGlobals object, as they would in uBlock Origin
const combined = '(() => {\nconst minScriptletGlobals = {};\n' + scripts.map(function (s) {
  return '((scriptletGlobals) => {\ntry {\n' + s + '\n} catch (e) {}\n})(minScriptletGlobals);'
}).join('\n') + '\n})();'
sender.executeJavaScript(combined)

Sharing scriptletGlobals matters too. Ghostery 2.20 uses it to let every scriptlet reuse the first snapshot of the browser's real functions. Without it, YouTube's six JSON.stringify scriptlets each wrapped the previous one, and every call ran 2⁶ = 64 times. With it, it runs 7 times.

Why YouTube showed ads, and the fix

Some scriptlets only work if they're in place before the page's own scripts run. YouTube's page starts with a script that writes the video's details, ads included, into a variable called ytInitialPlayerResponse. One rule sets a trap on that name first, so that when YouTube writes it, the ad part is thrown away. Set the trap after YouTube has written it, and it can't change anything any more.

Min used to send the scriptlets a moment too late. The page asked the main process for them, the main process ran them, and by then YouTube's script had already run. So on every newly opened YouTube page, the player got its ad data, and sometimes it played an ad.

Now the page's preload asks for its scriptlets as the page starts and waits for the answer (about 1 ms on YouTube, a fraction of that elsewhere). It runs them before anything else on the page, as uBlock Origin does. The test measure-youtube-ads.js opens three videos in new tabs, then clicks from each to another video:

Clicking from video to video was already ad-free, because YouTube changes video without loading a new page, and the scriptlets were in place by then. The first video in a fresh profile still takes about 15 seconds to start, with no ad: that's YouTube waiting about as long as the ad would have run. uBO Lite showed one such slow start too.

The bug in the first version of the fix

The page waits for the answer through a "synchronous" message. In Electron, the reply goes out the moment the code sets event.returnValue. The first version set it to "nothing" at the top, to be sure it always answered, so every page got nothing, and YouTube kept showing ads. The test caught it, because it checks whether the trap was really set first, not only whether an ad played.

Empty ad spaces

On 10 November we looked at the 9 "visible ad slots" the comparison counted for Min's blocker. None held an ad: the network rules had blocked every ad request. They were empty space the page had set aside for ads, such as a 276 px blank band across the top of CNN, or a grey box saying "Advertisement". The test measure-ad-slots.js found three different reasons, each with its own fix. With the first two fixed, CNN shows none of its 8 empty spaces and Hindustan Times none of its two; Allrecipes' one remains:

  1. A bug: the wrong domain. To pick a site's rules, the engine needs the site's main domain, for example cnn.com. Min gives it the address minus "www.", which is the same thing for www.cnn.com but not for edition.cnn.com. So on any address that doesn't start with "www.", the rules written for that site never apply. CNN's own hiding rules and its 8 scriptlets were all skipped. Giving the right domain removes all 8 of CNN's empty spaces. It also turns on the scriptlets written for Spotify's web player (open.spotify.com), YouTube Music and YouTube's mobile site. The fix was a few lines, using the same domain parser Ghostery itself uses (tldts). Fixed on 10 November. A test suite, adblock-cosmetic, now checks it without the internet: it tells Min that edition.cnn.com lives on the test computer, serves a small page there, and checks that CNN's rules hide its ad box and that CNN's scriptlet ran first. With the old line put back for one run, both checks fail.

  2. Generic rules Min never asks for. Most of EasyList's rules aren't about one site. "Hide anything with the class ad-slot" applies everywhere. The engine only hands those over when you tell it which classes, ids and links the page actually has. Ghostery's own add-on does that with a small script in every page, which watches the page for changes; Min didn't. On Hindustan Times this left a blank band above the header and an empty "Advertisement" box, which the comparison didn't even count. Adding the generic rules removed both, the same as uBO Lite. Built on 10 November, with Ghostery's own page watcher (a first version had a hand-written copy of it; it was swapped for Ghostery's the same day, because the project reuses what Ghostery already has rather than rewriting it). The watcher sends main the page's classes, ids and links, then only new ones as the page changes (when it starts is explained just below). Min adds one thing: the watcher stops while the tab is in the background or Min is minimized, and one scan catches up when the tab is shown again. Main looks up the matching rules and inserts them as CSS. Measured on seven sites, loaded and scrolled, three runs each: Min used about 74 seconds of processor time with it and about 69 without (about 7% more while pages load, close to the first version's 5%; one run with it took 90 seconds, which wasn't explained). The main process spent 20 to 30 ms in total answering the pages. While idle or minimized nothing was sent and the processor time was the same. Hindustan Times now looks the same as with uBO Lite.

    Something you may have noticed: a site's own rules are in place before the page is drawn. The generic ones need the page's classes, and those arrive with the page. Ghostery's and uBO Lite's watchers only start once the whole page has arrived, and Min's did too at first. So on a big news site an empty ad box could show for a moment while the page loaded, then vanish: CNN about 0.3 seconds, NDTV up to 0.9, YouTube's home page up to 1.6.

    A setting since 11 November: "Hide empty ad spaces while pages are still loading", in Settings → Performance, off unless you turn it on. With it on, in the tab you're looking at, Min starts Ghostery's watcher with the page's first bytes, so the rules arrive with the first parts drawn. The main process reads the setting each time a page starts and tells the page with its first answer, so a change applies to the next page you load, without a restart. Measured three times on the same seven sites, the boxes no longer show at all (YouTube 10 ms, about one frame).

    It isn't free. Real sites change from minute to minute, so the cost was measured again on seven made-up pages that are identical every run:

    • Memory: each tab that loaded while shown keeps about 4 to 5 MB more, even when Min is minimized. That was 25 MB more for seven tabs; the real sites showed 10 to 55 MB more. It's in the browser engine's own memory, not the watcher's.
    • Processor: pages take 13% more processor time while they load: 21% of one core instead of 18% here, or 1.3% of the whole processor instead of 1.1%. On real sites the difference was smaller than the normal variation between runs.

    Processor time while Min sits idle or minimized changes by at most 0.2 seconds a minute, and a tab loading in the background still waits until it has loaded. ("What the newest changes cost", in the memory chapter, compares this with no generic rules at all.) Since the project's main goal is a small footprint, it's off unless you turn it on. A box a page adds later is hidden within about 30 ms (2 or 3 frames).

    It doesn't make Min faster. Starting early can only add work while a page loads. The pages' first paint times jumped around too much between runs to show any difference. What you gain is visual: the empty box no longer appears and then disappears, which usually makes the text below it jump up. Speedometer, the usual browser speed test, wasn't run for this. Its tests run after the page has loaded and inside a frame the watcher doesn't watch, so no change is expected.

  3. An ad-recovery service. Allrecipes runs Ad-Shield, a company whose scripts put ads back for ad-blocker users. When it sees the ads were blocked, it rebuilds them with random class names (like harzsgqwhvznvy7ngmsvgy7), so no hiding rule can match them. It even rewrites the page's own functions so the page still sees the old names, which fooled the test until it read the page from a separate JavaScript world. The filter lists deliberately don't block Ad-Shield, because blocking it breaks sites. With uBO Lite, Ad-Shield never started on Allrecipes. That's most likely because uBO Lite feeds the page a harmless fake of Google's ad script (a stand-in), so the page thinks its ads loaded. Min can't serve stand-ins yet (the next section's "stand-ins that never arrive"). Fixing that would probably fix Allrecipes too, but that isn't proven.

Known limits

  • A bug found and fixed on 9 November: on a brand-new profile's very first start, Min tried to download the block lists before Electron was ready, failed, and used only the small built-in list for the first hour. Every new user started that way. Now the download waits until Electron is ready (app.whenReady() in fetchAdblockerList), and the full lists arrive about 2 seconds after the first start. The test suite adblock-first-start checks it.
  • Right after Min starts, while the saved engine is still loading, the first pages get their scriptlets a moment later, the old way.
  • Sometimes a video sits on a spinner for about as long as the ad would have run. This is YouTube's own delay for viewers whose ad didn't load.
  • Stand-ins that never arrive. For some well-known ad and analytics scripts, the lists don't say "block this" but "swap it for a harmless stand-in": an empty file, or a tiny fake of Google's ad script that reports "ads loaded fine". A site that waits for that script then carries on normally. Ghostery hands Min each stand-in as a data: address, where the file's whole content is written into the address itself. Chromium refuses to send a web request on to a data: address (ERR_UNSAFE_REDIRECT), so the request fails exactly like a blocked one. uBlock Origin Lite serves its stand-ins from its own extension files, which Chromium allows: in the 7 November comparison it swapped 78 requests on the five sites this way, while Min's blocker swapped none. The ads stay blocked either way. The risk is a site that waits for a script that never comes, so a video player that never starts, a button that does nothing, or an "ad blocker detected" message. None has been seen so far. The fix would serve the stand-ins from a Min address that Chromium accepts; it's only worth building if a site breaks.
  • When an ad-blocking extension takes over normal tabs (Chapter 18), everything in this chapter applies to private tabs only.
Chapter 11

Permissions

How a site asks for your camera, and how your answer is remembered. Most of this is your own work.

Sites must ask before using the camera or microphone (media), showing notifications, capturing the mouse pointer (pointerLock) or sharing your screen (display-capture). Full screen and copying to the clipboard are always allowed. Electron hands these decisions to Min through three hooks, all set up in main/permissionManager.js:

  • setPermissionRequestHandler: a site is asking. Min may need to show a prompt.
  • setPermissionCheckHandler: a site is checking quietly (for example reading Notification.permission). Min must answer straight away, without a prompt.
  • setDisplayMediaRequestHandler: a site wants to share the screen. Min lists screens and windows with desktopCapturer.getSources and lets you pick one. On Windows it can include system audio.
  • Saved answers live in settings.json under sitePermissions, keyed by site name, for example {"example.com": {"media:video": "allow", "notifications": "block"}}. Private tabs never save.
  • "Allow for this session" answers are kept in memory, tagged with the session they were given in, so private tabs and normal tabs don't share them.
  • Live indicators: mediaTracker.js reports when capture starts and stops (media-access-status). The tab icons and the memory trimmer both use that information.
  • Site settings in pages/settings lets you review and change saved answers.
Chapter 12

Memory and the background

Your goal is a second browser that stays out of the way. These are the parts that make that happen.

Trimming memory

Windows keeps each process's recently used memory in physical RAM, called its working set. ext/windows/trimMemory.exe (source in scripts/trimMemory.cs) calls Windows' EmptyWorkingSet, which moves that memory out of RAM so other programs can use it. The cost is a small stutter when the page is used again and Windows reads it back in.

  • main/main.js trims the whole app when you minimize Min, 4 seconds after it loses focus, and every 90 seconds while it stays unfocused. This only works in the installed browser, because in the dev build every process is called electron.exe.
  • main/viewManager.js trims tabs that have been in the background for at least 30 seconds, every 60 seconds. It also trims the extra processes their ads and embedded videos run in (cross-site frames, see site isolation in the glossary). You can limit this to the times Min isn't in use (Settings → Performance, below).
  • Both skip tabs that are playing sound or video or using the camera, microphone or screen sharing. They also pause while a download is running.

Memory priority

Windows gives every process's memory a priority from 0 to 7; normal is 5. When RAM runs short, Windows takes memory from low-priority processes first. Chromium already lowers background tabs' CPU priority but leaves their memory at 5. After trimming a background tab, your fork also sets its memory priority to 2 (trimMemory.exe --memory-priority low). So when a game or any other program needs RAM, Min's background tabs are the first to give it up, and your current tab keeps its memory.

The tab gets normal priority back straight away when you click it, when it starts playing sound, or when it starts using the camera or screen sharing.

Trimmed isn't the same as freed

Task Manager's "Memory" column shows the working set, the part in RAM right now. Trimming shrinks that number, but Windows still reserves the memory for Min (its private bytes), keeping it on standby or in the page file. We tested whether background pages could actually give memory back if asked: every background page in 10 tabs was told to collect garbage and then sent Chromium's "memory is critical" signal.

A live page's memory is its real working state: the JavaScript heap, the page's elements, compiled code. There's almost nothing to release. Only hibernation, which closes the page's process, frees memory in bulk. Tabs that must stay alive, such as chats and calls, keep about 100–160 MB each.

Hibernating tabs

Every 5 minutes, checkSmartHibernation looks for tabs you haven't used for 15 minutes and closes their views to free memory completely. It used to wait an hour; we lowered it after measuring that 10 background tabs hold about 1.45 GB that hibernation frees. The tab stays in the tab bar and reloads when you click it. A tab is kept alive if any of these are true:

  • it's selected in any window, or was used in the last 15 minutes;
  • it's playing media or capturing;
  • a download is running;
  • the site has notification permission;
  • the page has text you typed and haven't sent, an open WebSocket (chat apps), an "are you sure you want to leave" handler, or playing media.

"Text you typed" means fields you actually changed. The first version counted any field with a value, and since checkboxes always have one and many sites pre-fill their search box, 6 of 8 test tabs could never hibernate.

Where the memory really goes

On 7 November we measured where Min's memory goes, to see what else could be cut. The short answer: Min's own code is small. Most of each process's memory is Chromium and Electron themselves, which every Electron app pays.

  • The GPU process grows with what sites draw, not with how many tabs are hidden: 138 MB with one simple tab, 145 MB with nine, 197 MB with YouTube, GitHub and others open. Minimizing or hibernating didn't shrink it.

Min saves your tabs every 30 seconds, and was meant to save once more as it closes, from the UI page's "before unload" event. That event never fired. A review of that fix found it only worked while Min's window was the one you were using. The UI saves only when its window is focused, so that with several windows open just one of them writes the file. But Min is the browser you leave in the background: closed from the taskbar, or when Windows shuts down, no window is focused, and the save did nothing. A new check showed it: a tab opened 5 seconds before quitting, with Min's window in the background, was lost. Now the main process tells one window to save even if it isn't focused (the last one you used, or the last one open). Windows shutting down is a separate case, because Windows doesn't send a normal "close": it first asks every window whether it's ready, and Min now saves when it's asked. session-restore passes all 5 checks. Settings

The main process owns settings.json. The UI reads it at startup and changes values with settings.set(key, value), which sends settingChanged to the main process. The main process saves the file and tells every other window. Code that cares about a setting calls settings.listen('darkMode', fn). The min:// settings page talks to the UI through postMessage and the settingsPreload.js bridge.

History and full-text search

When a page finishes loading, its text goes to places.js in the UI. From there it goes through a private MessageChannel to a hidden window, js/places/placesService.html, which stores it with the Dexie library in IndexedDB.

  • Words are lowercased and reduced to their stems, so "running" matches "run", and indexed for fast lookup.
  • History and bookmarks share one table, with a flag that marks bookmarks.
  • History that isn't bookmarked is deleted after 42 days.
  • The hidden window keeps a copy in memory so suggestions appear instantly as you type.

The smaller features

  • Passwords: the built-in store, Bitwarden or 1Password (through their command-line tools). passwordFill.js handles the page side.
  • Downloads: main/download.js watches will-download and streams progress to the download bar (js/downloadManager.js). PDFs open in pages/pdfViewer, which uses Mozilla's pdf.js.

Chapter 14

Userscripts

Small scripts you install to change how a website looks or works. Your fork runs the same ones Tampermonkey does, without an extension.

A userscript is a JavaScript file with a comment block at the top that says which sites it's for and what extra powers it needs. Sites like Greasy Fork and OpenUserJS host thousands of them, from Return YouTube Dislike to dark themes and download buttons. Other browsers need an extension such as Tampermonkey to run them. Your fork has it built in: turn on "Enable user scripts" in Settings.

The header block

// ==UserScript==
// @name         Min userscript demo
// @match        https://example.com/*
// @run-at       document-idle
// @grant        GM_setValue
// @connect      api.github.com
// ==/UserScript==
  • @match and @include say which pages the script runs on; @exclude says where it doesn't.
  • @run-at says when: before the page's own scripts (document-start), once the page has loaded (document-end), or a moment later (document-idle, the default).
  • @grant asks for Greasemonkey functions, the script's extra powers: saving data, contacting other sites, showing notifications and so on.
  • @connect lists the other sites the script may contact.
  • @require names libraries (like jQuery) that are downloaded once, when the script is installed.

What happens when a page loads

  1. The preload (Chapter 08) asks the main process "which scripts match this frame?" It asks synchronously: the page waits for the answer, about 0.1 to 1 ms, so a document-start script really runs before the page's first script.

  2. The main process (main/userscripts.js) checks the frame's address against each script's rules (js/util/userscriptMatching.js) and sends back the matching scripts' code and saved data.

  3. The preload runs each script at its @run-at moment. Scripts also run inside iframes unless they say @noframes, and they skip private tabs unless you allow it in Settings.

Giving scripts powers without giving them to the website

A userscript has to run in the page's main world, because it works with the site's own variables (Tampermonkey calls the page's window unsafeWindow). But its Greasemonkey functions must stay out of the website's reach. If a site could call GM_xmlhttpRequest, it could read other sites while you're signed in to them.

The trick: the preload turns each script into a function whose parameters are the Greasemonkey functions, then runs it in the main world with Electron's contextBridge.executeInMainWorld. The script receives the functions as arguments, and they never appear on window. The functions themselves stay in the preload's isolated world and ask the main process for anything privileged. We checked that this works on a page with strict security rules, on GitHub and on YouTube.

Greasemonkey functionsWhat they do
GM_getValue, GM_setValue…Save the script's own data. Other tabs running the script see changes straight away.
GM_addStyle, GM_addElementAdd CSS or elements, even on sites whose security rules would block them.
GM_xmlhttpRequestFetch from another site, sent by the main process with your logins. Only to the page's own site and the domains in @connect.

Installing and updating

  • Open any .user.js link and Min shows its install page (pages/userscriptInstall) instead of the code. It lists the sites the script runs on, the sites it can contact and what it can do, with warnings for scripts that run everywhere or can reach any site.
  • Min notices .user.js files in the main process, from the response's headers (main/download.js), not in the page. GitHub serves raw files with a security rule that switches off the preload, so the page can't report itself.
  • Installed scripts are checked for updates once a day. An update installs by itself unless it asks for more (new sites, domains or functions) or you edited the script. Then Settings shows "Review update".
  • Settings lists your scripts: switch one off, edit it (in Notepad), remove it (to the Recycle Bin), create a new one, or check for updates.

On Windows, double-clicking a .js file doesn't open an editor; it runs the file with Windows Script Host. Min opens scripts in Notepad on purpose.

The automated test suites

Everything that was ever checked while building Min's features is kept as a script in test/e2e. A script starts Min, clicks and types through the DevTools connection, and checks what happened. Run them all with:

npm run build

Errors you'll meet

  • "Object has been destroyed": code used a tab or window after it closed. Check isDestroyed() first.
  • "An object could not be cloned": you sent something through IPC that isn't plain data, such as a function or a DOM element.
  • Hundreds of "X is not defined" from npm test: lint noise caused by the glued main files (Chapter 04).
  • New text shows as "undefined": the string didn't make it into dist/localization.build.js. The language files use Windows line endings; a line added with Unix ones makes the build silently drop strings. Keep each file's line endings the same.
  • electron.clipboard is undefined in the UI: since Electron 44 only the main process has it. Use ipc.invoke('clipboardWrite', …).
  • A box saying "A JavaScript error occurred in the main process": code in the main process threw an error nobody caught. While the box is open, the main process is frozen: tabs stop loading and nothing answers until you click OK. Min hit this when it downloaded its ad-block lists with Node's own fetch, which has a bug in Node 24; it now uses Electron's net.fetch. Test scripts catch these errors themselves (process.on('uncaughtException')), so the box never appears and the script stops instead of hanging.
Chapter 18

Chrome extensions

Chrome extensions, installed as easily as in Chrome: the Web Store's own "Add to Chrome" button works, extensions update themselves, and their toolbar buttons, popups, menu items and shortcuts work. An ad-blocking extension like uBlock Origin Lite can take over from Min's own ad blocker, the features popular extensions rely on (screenshots, downloads, side panels, sign-in windows) work, and idle extensions shrink while Min isn't in use.

Electron can load Chrome extensions, but it only implements part of Chrome's extension system. A free library, electron-chrome-extensions, fills in much of the rest: tabs and windows, toolbar buttons and their popups, right-click menu items, keyboard commands. Min adds what users expect from Chrome: installing from a file or the Web Store, a permission review, a list in Settings, and updates.

What an extension is

  • A folder with a manifest.json: its name, version, permissions, and which files do what.
  • A background worker: the extension's own invisible page that listens for events (a tab changed, a message arrived, an alarm went off). It runs in a process of its own.
  • Content scripts: code it adds to the websites it's allowed on, like a userscript.
  • Its own pages, at chrome-extension://<id>/…: popups, options, welcome pages.

The Chrome Web Store ships extensions as .crx files: a zip file with a signed header in front. The signature proves the file comes from the extension's developer, and the developer's key also decides the extension's id, a 32-letter name like eimadpbcbfnmbkopoojfekhnkhdbieeh (Dark Reader).

What happens when you install one

  1. You click "Add to Chrome" on the Chrome Web Store, or in Settings → Extensions pick a .crx file (or an unpacked folder, for developers).

  2. Min checks the signatures (js/util/extensionPackages.js, unit-tested) and reads the manifest. A file from the Web Store carries two: the developer's, and the store's own, which proves Google's store served it.

  3. A dialog shows what the extension can do: "Read and change all your data on all websites", "Manage your downloads" and so on. Nothing is installed until you say yes.

  4. Min unpacks it into your profile, keeping the developer's key so the id matches Chrome's, and records it in extensions.json.

  5. The first time, Min starts the extension system; then it loads the extension and tells it "you were just installed". Dark Reader, for example, opens its welcome page.

The Web Store's "Add to Chrome" button

The store's page talks to the browser through a hidden Chrome-only API, chrome.webstorePrivate: "is this extension installed?", "install it", "remove it". Electron doesn't have it, so on chromewebstore.google.com only, a small preload (js/preload/webStore.js) adds it to the page and passes each call to the main process. Main accepts these calls from the store's own page and nowhere else.

When you click the button, Min shows its permission review, downloads the extension from Google's server, checks both signatures and that it's the extension you clicked, and installs it. The button then turns into "Remove from Chrome", which asks first and removes it. The store still calls Min "Chrome" and shows a "Switch to Chrome" banner, because Min doesn't claim to be Google Chrome; installing works anyway.

One surprise on the way: an old Min fix for Google's websites replaced the page's chrome object on every google.com site, which threw away the store's API. The store is now left alone.

Updates

Every few hours (and when you click "Check for updates" in Settings), Min asks Google's update server, in one request, whether any installed extension has a newer version. Chrome does the same. An update that asks for nothing new installs by itself. One that wants more, say access to every website, waits: the old version keeps running, Min shows a notification once, and Settings offers "review the update", which lists only what's new.

Toolbar buttons and popups

Most extensions have a button in Chrome's toolbar. In Min, they appear in the top bar, just right of the "+" (new tab) button, with the extension's icon and its badge: the small number or word some extensions show, such as an unread count. The extension library keeps track of each button's icon, title, badge and popup, and tells Min whenever one changes. Min then redraws the buttons for the tab you're looking at, since a badge can differ from tab to tab.

  • Click: the extension's popup opens as a small window right under its button. Click again, or anywhere else, to close it. An extension without a popup is told it was clicked instead.
  • Right-click: the extension's name (opens its store page), its own menu items, Options, "Remove from Min…" and "Manage extensions".
  • On a page: items extensions add to the right-click menu ("Translate this", "Save to…") appear after Min's own.
  • Keyboard shortcuts an extension suggests (Alt+Shift+D, for example) work, unless Min already uses those keys. Then Min's shortcut wins, as in Chrome.
  • Options pages open in a tab, from Settings or from the button's menu.
  • Private tabs show no extension buttons, since extensions don't run there.

Dark Reader sets its icon to "../icons/…": a path relative to its background script's folder, which Chrome allows. Min resolves these like web addresses, which can never point outside the extension's own folder.

Nothing runs until you install one

The extension library adds a small script to every page and starts with the browser, so Min only starts it once an extension is turned on. With none installed (or after removing the last one), the library isn't even loaded. That's the "zero cost" rule you set.

With some installed, each running extension costs about one process and around 80 MB: Dark Reader, Bitwarden and uBlock Origin Lite together added three processes and 248 MB, and used no CPU while idle. Extensions only run in normal tabs, never in private ones.

While Min isn't in use (no Min window focused), extensions' processes are trimmed every minute like background tabs (Chapter 12), and Windows gets to reuse their memory first. Each background worker tells Min its process when it starts. In a test, Dark Reader's and Bitwarden's processes went from 119 and 187 MB to about 3 and 10 MB once Min was minimized, and both kept working. While you use Min they're left alone, because a trimmed worker would have to page back in on every page you load. One showing a popup or a side panel, or playing sound, is never touched.

Gaps Min fills itself

Testing with real extensions turned up four things that Electron and the library get wrong, which main/extensions.js and js/preload/extensionSupport.js fix:

  • "You were installed" and "the browser started" (onInstalled, onStartup) were never sent. Many extensions set themselves up in those events. Min now remembers what happened and tells each extension when its background worker starts.
  • Background tabs jumped to the front. The library assumes every new tab is the one you're looking at and asks Min to switch to it, so with any extension installed, Ctrl+click would have opened the link in front of you. Min now adds tabs quietly, and a tab only counts as active when Min shows it.
  • Two names for the same thing. Chromium offers extension features under two names, chrome and browser. The library only fills in chrome, and uBlock Origin Lite uses browser, so it crashed on start. Min makes both names point to the same object.
  • Installing one extension broke the others (found 9 November). Whenever an extension is added, removed, turned on or off, Chromium rebuilds some of the chrome objects inside every other extension that's already running, and the rebuilt ones lack everything the library and Min added: even "open a tab" was gone. The extension stayed half-broken until Chromium happened to restart it. Dark Reader showed it: with Bitwarden installed after it, its popup stayed on "Loading, please wait". Now each extension keeps its finished objects, and Min tells them all to put those back a moment after any extension is loaded or unloaded. (The error Dark Reader logged, about a missing "may I read local files?" function, first looked like something Electron lacks. The extension library does have it; the rebuild had thrown it away.)

Testing 53 popular extensions

A script read their code for the Chrome features they call and compared that with what Min offers. Then it installed each one in turn and recorded the errors it hit. All 53 install, and their background workers run. Along the way it found three serious bugs:

  • SponsorBlock stopped at start. The extension library "freezes" the chrome object so nothing can be added to it. Real Chrome doesn't, and SponsorBlock adds to it. A second small preload, run just before the library's, skips that one freeze.
  • Awesome Screenshot crashed the whole browser when its popup opened. The extension makes a hidden "offscreen" page and asks it for the list of cameras and microphones. The extension keeps working, minus recording.
  • Installing Wappalyzer froze Min for 30 seconds. It has 13,000 files, and Min wrote them one by one while everything else waited (Windows scans each new file). Min now writes them in the background, 16 at a time: faster, and the window stays responsive.

What extensions see of your tabs

Tab managers such as OneTab and Session Buddy ask the browser for the window's tabs, in order, and listen for tabs opening and closing. The extension library only knows tabs that have a page loaded, and it kept them in the order they were opened. Min has tabs without a page: ones it hibernated to save memory (Chapter 12), and the ones it brings back at startup, which only load when you click them. A test on 9 November (extensions-tabs) showed what extensions got:

  • Tabs in the wrong order. Min puts a new tab right after the current one, so three tabs opened from tab A read A, D, C, B in the tab bar, while extensions were told A, B, C, D.
  • The wrong position for a tab asked about on its own: always 0.
  • A hibernated tab vanished, and extensions were told it had closed. When you clicked it again, it came back as a brand-new tab.
  • After a restart, only the one tab you were looking at.

Now each window's UI sends the main process its tabs in order whenever they change, only while extensions are running (main/extensionTabs.js). The main process puts the library's list in Min's order and numbers each tab by its place. A tab without a page is listed as "discarded", which is what Chrome calls a tab it has unloaded to save memory. When Min hibernates a tab, extensions hear "this tab was discarded" instead of "this tab closed". When it loads again, they hear "this tab was replaced by a new one with this id", as Chrome tells them for a discarded tab that comes back with a new id. The test now passes all 8 checks; it failed 5 before (the other 3 hadn't been able to run).

To do this, Min has to reach inside the library: its private list of tabs and the way it sends tab events, neither of which the library promises to keep the same. So the first thing extensionTabs.js does is check that every piece it uses is still there. If a future version of the library has changed one, Min leaves the whole feature off and writes a line in its log saying so. Extensions then see only what the library alone shows, and Min doesn't crash. Two kinds of check watch this. extensions-tabs checks Min's log has no such line. electron-workarounds turns Min's tab list off and checks the library still gets all three things wrong: the order, the index, and a hibernated tab reported as closed. When one of those starts passing after an upgrade, that part of Min's fix can go.

Since 12 November an extension can also act on a hibernated tab, as tab suspenders and session managers do. Reloading it loads it again in the background, switching to it shows it, and muting it is remembered for when it loads. Before, each of these failed with an error inside the library, because the placeholder Min puts in the library's list for a sleeping tab couldn't do what the library asks of a real page. extensions-tabs now has 13 checks.

What an extension may see without permission

When you install an extension, Min shows what it asks for: "read your browsing history", "read and change your data on these sites", and so on. Chrome enforces those answers. An extension that didn't ask for the "tabs" permission can't read your tabs' addresses, and one that didn't ask for "cookies" can't read cookies, which is what keeps you signed in to websites.

A hole found on 12 November

The extension library Min uses never checked any of this. It gave every extension every feature it has and answered whatever was asked. A test extension that asked for almost nothing could list every tab's address and read a website's sign-in cookie. Nothing suggests any real extension did this; it was found by reading the library's code while reviewing the tab list, then confirmed with that test extension.

Min now checks permissions itself, at the one place where all of the library's answers and events pass (main/extensionPermissions.js):

  • A tab's address, title and icon go only to extensions with the "tabs" permission, or with access to that website. Other extensions still see that the tab exists, without those details.
  • "activeTab" works as in Chrome: when you click an extension's button on a page, it may see that page, until the tab goes to another website.
  • Cookies need the "cookies" permission and access to the cookie's website.
  • Features an extension never asked for (cookies, navigation events, notifications, menu items) aren't there for it at all.
  • One extension can't pretend to be another. The library's messages to main carry the extension's name, and any extension's code could write another's there, one with more permissions. Main now checks who really sent each message.
  • Permissions an extension asks for later ("optional" ones) must be in its manifest, so you saw them at install; what you allow is remembered after a restart (the library forgot it), and the extension can give it back.
  • A screenshot of the page you're looking at needs "activeTab" in effect (you just clicked the extension on that page) or access to the site.

The new suite extensions-permissions (22 checks) covers this, and electron-workarounds checks that the library alone still gives everything away, so a future version that fixes it will show up there. What wasn't checked: the library's remaining features, and the extension features Electron provides itself.

Password managers and Min's "save password?" bar

Bitwarden, 1Password, LastPass and Dashlane can tell the browser to stop offering to save passwords, so that only they offer. Their code shows all four do it: Bitwarden and 1Password from an option, LastPass when you sign in, Dashlane as soon as it's installed. Min answered "done", then kept showing its own bar anyway, so after signing in you could get two "save this password?" offers. It also forgot the setting at every restart.

Now Min keeps each extension's privacy settings in extensions.json, as Chrome keeps them. While a password manager has the setting off, Min's bar stays away. Turn the extension off or remove it, and Min offers again. Filling in passwords you already saved in Min isn't affected. The test extensions-passwords passes all 8 checks; it failed 3 before.

Letting an extension block ads

Some extensions filter network requests: uBlock Origin Lite, privacy tools, some password managers. Electron switches that off for extensions as soon as the app itself watches requests in the same session, and Min watches them in four places (Chapter 09). So it's one or the other: Min's ad blocker, or the extension's.

  1. When you install such an extension, its review says: "Adding it turns off Min's ad blocker in normal tabs, so that this extension blocks there instead; private tabs keep Min's ad blocker."

  2. Min removes its four hooks from normal tabs' session, and the extension's blocking starts working. Private tabs have sessions of their own, keep the hooks, and keep Min's ad blocker (extensions never run there anyway).

  3. Settings → Privacy now shows a switch: "Let uBlock Origin Lite block ads and trackers in normal tabs, instead of Min's ad blocker". Turn it off, or turn off or remove the extension, and Min puts its hooks back. Reload open tabs after switching.

Two surprises came up along the way:

  • Rule lists start switched off. Ad-blocking extensions ship their rules as lists in the manifest. Chrome turns on the ones marked "enabled"; Electron doesn't. uBlock Origin Lite turns them on itself, but simpler extensions don't, so after installing Min opens a hidden page of the extension and turns them on from inside it. Electron remembers that across restarts.
  • The hooks had other jobs. Without them, Min does those another way in normal tabs:
    • Google sign-in's Firefox identity and the removal of tracking parameters (utm_source and friends) become rules of a tiny built-in extension, ext/minNetworkHelper, which Min loads only in this mode.
    • Opening a .user.js address is spotted when the tab starts loading it, and files (for "save page") are recognised once they've loaded.
    • Reader view asks the main process to fetch the article, since its own fetch is no longer allowed.
    • PDFs open in Chromium's built-in viewer instead of Min's.

Also lost in this mode: the "block all scripts / images" option and the shield button in the address bar (both are Min's ad blocker's). Min's "blocked" counter doesn't count what the extension blocks.

Only the current kind of extension

Chrome extensions come in two formats. The older one, Manifest V2, ran a hidden page in the background all the time and could stop any network request in flight. The current one, Manifest V3, uses a background worker that sleeps when idle and blocks requests by handing the browser a list of rules. Chrome stopped running Manifest V2 extensions in 2025, and the Chrome Web Store removed the last of them on 31 August 2026. Edge and Opera are following; only Brave keeps four ad blockers by hosting them itself.

Min does the same. checkExtensionManifestVersion in main/extensions.js turns one away wherever it could come in: a .crx file, an unpacked folder, the Web Store page, an update. One installed before this change isn't loaded: Settings lists it with the reason, and Remove still works. The bits of Min that only existed for the old format are gone.

A few things still can't work, because Electron lacks what they need or Min hasn't added it: Tampermonkey and Violentmonkey (Min's own userscripts replace them), signing in with your Google account through Chrome, recording a tab or the screen (Loom, Awesome Screenshot's video), tab groups and moving tabs, bookmarks and history for extensions, the address-bar keyword feature (omnibox), the list of installed fonts (Dark Reader's font picker), per-site content settings, Google's push messages (Checker Plus for Gmail), and a new-tab page from an extension (Momentum).

Do these gaps break anything? We checked on 9 November. No: every one of the 53 extensions installs and starts, and none of Min's own features use these functions. When an extension calls a function Min doesn't have, only that one action fails, so one feature of that extension doesn't work while the rest does. The two gaps that made working features behave wrongly were fixed that day: the tabs and the password bar, above. Of the rest, some need new UI (a screen picker for recording, address-bar keywords, tab groups), some could be built without UI (moving tabs, bookmarks and history for extensions), and some can't be done in Min at all (Chrome's Google sign-in, Google's push messages, recording a tab's sound).

That list comes from a function-by-function check run on 9 November (measure-extension-survey.js --scan). The first survey compared mostly by feature area, and by hand, so it missed single missing pieces inside an area that otherwise works, like chrome.tabs.TAB_ID_NONE, a fixed value that six of the 53 extensions use (Bitwarden and 1Password among them), now added. The scan reads every chrome.* name the 53 extensions' code mentions (466 of them), then looks each one up in a test extension that asks for every permission they ask for. Apart from what's listed above, everything Chrome has is there. Not covered: the pages extensions add to DevTools.

Chapter 19

Security: keeping websites in their place

A browser's first job is to keep whatever a website does inside that website. In November 2026 a review of Min's code listed 14 ways it might fail at that. Each one was tried for real before anything changed: 13 were real, and all 13 are fixed.

Chapter 02 showed the big walls: websites run in sandboxed processes without Node.js, and Min's own interface runs somewhere else. This chapter is about the smaller doors in those walls, the places where Min deliberately lets a page ask for something, and what happens when a website knocks on one it shouldn't.

Min's own pages are special

Settings, the "server not found" page, the new tab page, the userscript install page and the PDF viewer are web pages too, at addresses starting with min://app/. But they're trusted: through the preload (Chapter 08) they can change any setting, install userscripts, and turn extensions on and off. And they all share one origin (the scheme and host of an address, here min://app), which is the unit browsers use to decide who may touch whose page.

Many of them also read their own address. The error page is min://app/pages/error/index.html?ec=-105&url=https://example.com: its "Try again" button goes to whatever url= says. That's fine while only Min opens these pages. Until 13 November, a website could too:

  1. A website runs location.href = 'min://app/pages/error/index.html?url=javascript:…'. Nothing stopped a page from sending its own tab to Min's error page.
  2. The error page shows "Server not found", with its "Try again" button already selected. Pressing Enter, or clicking it, sets window.location to the javascript: address, which doesn't go anywhere: it runs the code after the colon, inside Min's own page.
  3. That code asks Min, as Settings would, to change a setting. The test suite did exactly this, and the setting changed. A real attacker could have turned off ad and tracker blocking, or pointed Min at a proxy of their own.
The fix: two locks
  • Websites can't go to min: addresses. main/viewManager.js refuses any navigation, redirect or new window to a min: address unless Min itself started it (the address bar, opening a PDF, the error page after a failed load) or one of Min's own pages did. Chromium tells main who started each navigation (its initiator), so this is a few lines.
  • Every internal page treats its own address as untrusted input. Extensions may still open Min's pages, as Chrome lets them open chrome:// pages, so the pages themselves must be safe. The error page only tries again with web addresses, and has a CSP that forbids inline code, so a javascript: address couldn't run anyway. The userscript install page only reads a file from your disk if Min itself opened the page for that file: before, an extension with no permissions at all could have it read any file.

The address bar must tell the truth

The address bar is how you know which website you're talking to. Min used to change it as soon as a navigation started. So a page could start going somewhere that never arrives: a server that answers "204 No Content" (nothing to show) leaves the old page on screen. The test page did location.href = 'http://localhost:…/nocontent', and Min showed the other site's address above the first site's page. With a bank's address there, that's a convincing fake.

Chrome's rule, which Min follows now: when Min starts a navigation (you typed an address), it shows the new address at once; when the page starts one (a link, a script), the address changes only when the new page actually arrives. And if a navigation ends without a page, the address goes back to the page that's really there.

What it changed elsewhere

Parts of Min found a tab by the address it was going to. The PDF viewer did: after the fix, a PDF opened from a link never showed, because the tab still had the old address. The suites caught it, and the main process now tells the interface the tab's id instead. Lesson for later: find tabs by id, never by address.

Exercises

Small, safe changes that touch each part of the browser. Do them in order, on a new branch, with npm start running.

1 · Poke the tab model
  1. Open the UI's DevTools with Ctrl+Shift+Alt+I.
  2. In the console, type tabs.get() and look at the fields.
  3. On a tab playing sound, type tabs.update(tabs.getSelected(), { muted: true }). The mute icon appears, but the sound keeps playing.

  5. Type tasks.on('tab-updated', console.log), then load a page and watch the events arrive.

This teaches you that the UI is drawn from a data model, and that changing the model alone doesn't change the page. That's why browserUI.js always updates both.

2 · Change a word in the interface
  1. In localization/languages/en-US.json, change "newTabLabel": "New Tab" to "Blank Tab".
  2. Run npm run build, then restart the dev build.
  3. Open a new tab and look at its title.

This teaches you how translations flow into every process through l().

3 · Add a keyboard shortcut

In js/defaultKeybindings.js, inside initialize, next to the other shortcuts, add:

keybindings.defineShortcut({ keys: 'mod+shift+y' }, function () {
  console.log('Selected tab:', tabs.get(tabs.getSelected()).url)
})

Save, press Alt+Ctrl+R, then press Ctrl+Shift+Y and check the UI console. This teaches you UI code and the reload cycle.

4 · Write a suggestion plugin

Create js/searchbar/wordCountPlugin.js:

const searchbarPlugins = require('searchbar/searchbarPlugins.js')

function initialize () {
  searchbarPlugins.register('wordCount', {
    index: 1,
    trigger: function (text) { return text.startsWith('wc ') },
    showResults: function (text) {
      searchbarPlugins.reset('wordCount')
      const words = text.slice(3).trim().split(/\s+/).filter(Boolean).length
      searchbarPlugins.addResult('wordCount', { title: words + ' words' })
    }
  })
}

module.exports = { initialize }

Then add require('searchbar/wordCountPlugin.js').initialize() to js/default.js, next to the calculatorPlugin line. Reload, and type wc hello there world in the address bar. This teaches you the plugin system and how modules start up.

  1. In main/filtering.js, find handleRequest and the block that starts if (match) {. Add console.log('blocked', details.url) inside it.
  2. Quit and restart the dev build (main-process code doesn't reload).
  3. Open a news site and watch the terminal.
  4. Remove the line when you're done.

This teaches you main-process code, network hooks and where logs appear.

6 · Follow a message from end to end
  1. Search the project for set-window-title. You'll find a sender in js/browserUI.js and a receiver in main/main.js.
  2. Read both, then do the same for updatePermissions and hibernateTab.

This teaches you the header block, @grant, and that the site itself can't see GM_setValue: type typeof GM_setValue in the page's DevTools console.

Glossary

Background worker
An extension's invisible page (a service worker) that reacts to events: tabs changing, messages, alarms. It runs in a process of its own and may stop when idle.
BaseWindow
An Electron window that holds views. Min's window holds the UI view plus the selected tab's view.
Breaking change
A change in a new version of a library that makes old code stop working, so the code has to be updated when you upgrade.
Browser engine
The part that turns HTML, CSS and JavaScript into pixels. Here, Chromium.
Chromium
The open-source engine behind Chrome, Edge, Brave and Electron.
Client Hints
Sec-CH-UA headers that tell sites which browser you use, in addition to the user agent.
Content script
Code an extension adds to the websites it's allowed on, much like a userscript.
Context isolation
Running a preload in its own JavaScript world, so the page can't reach it.
contextBridge
Electron's safe way to hand values and functions across the two worlds. Userscripts get their Greasemonkey functions through it.
Cosmetic filter
An ad-blocking rule that hides elements with CSS instead of blocking downloads.
CRX
The file format of Chrome Web Store extensions: a zip file with a signed header. The developer's key in it decides the extension's id.
CSP
Content Security Policy, a response header that tells the page what it may load. Ad blockers sometimes add to it.
declarativeNetRequest
The way Chrome's newer (Manifest V3) extensions block or change network requests, by handing the browser a list of rules.
Deprecated
Still works, but marked for removal in a later version. Replace it before it's gone.
DevTools Protocol (CDP)
The interface DevTools uses to control Chromium. Scripts can use it too, through a remote debugging port.
Electron
Chromium plus Node.js, for writing desktop apps in JavaScript.
Filter list
A text file of ad-blocking rules, such as EasyList or uBlock Origin's filters.
Fuse
A switch baked into the Electron executable to turn off a feature for good.
Greasemonkey functions
The extra powers a userscript can ask for with @grant, such as GM_setValue and GM_xmlhttpRequest. Named after Greasemonkey, the first userscript manager.
Hibernation
Closing a background tab's view to free memory, while keeping the tab so it reloads when clicked.
IPC
Messages between processes, each with a channel name and plain data.
Isolated world, main world
Two separate sets of JavaScript variables over the same page. The preload uses the first, the site's own scripts the second.
Main process
The single, privileged process that starts first and controls windows, tabs, the network and files.
Manifest
An extension's manifest.json: its name, version, permissions and files.
Memory priority
Windows' ranking of whose memory to take first when RAM runs short, from 0 to 7 (normal is 5). Min gives background tabs 2.
Origin
The scheme, host and port of an address (https://example.com, min://app). Browsers let pages of one origin read each other, and keep different origins apart.
Occlusion
A window being completely covered by other windows. Chromium can treat a covered window as hidden.
Preload script
Min code that runs inside every page before the page's own scripts, and can message the main process.

Memory Windows has reserved for one process, whether it's in RAM or not. Trimming doesn't lower it; closing the process does.

The folder holding settings, history, passwords and sessions: %APPDATA%\Min.

A process that shows web content: Min's UI, or a website.
Sandbox
A renderer locked away from the operating system: no files, no programs, no Node.js.
Scriptlet
A small script from a filter list that changes a site's JavaScript, for example to strip ad data.
Session
A set of cookies, cache and storage. Normal tabs share one; each private tab gets its own.

Chromium putting each website, and its cross-site frames, in separate processes.
SPA
A single-page app, like YouTube, that changes pages without reloading. That's why some code also listens for pushState.
Spoofing
Making something look like what it isn't: another site's address over your own page, or one extension posing as another.
Squirrel
The Windows installer and updater system Min's setup file uses.
Task
Min's name for a group of tabs.
User agent
The text a browser sends to identify itself, such as "Chrome/150 on Windows".
Userscript
A JavaScript file you install to change how certain websites look or work, described by its ==UserScript== header.
webContents
Electron's object for one loaded page: navigate it, reload it, run code in it, listen to its events.
WebContentsView
A rectangle in a window that shows one webContents. Each Min tab has one.
webRequest
Electron's hooks into every network request of a session.
Working set
The part of a process's memory currently in physical RAM. Trimming shrinks it.
